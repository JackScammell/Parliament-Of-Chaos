# Probe corpus for scripts/ci/conformance.py check 7 (reviewer-verdicts).
#
# Replayed by check 8 (probe-corpus) on every gate run, and standalone via
#   python3 scripts/ci/conformance.py --self-test
# through the SAME predicate the real check uses (scan_verdict_line), so these
# probes exercise the shipped detector rather than a parallel copy of it.
#
# Format:  <DEFECT|CONTROL><whitespace><one probe line>
#   DEFECT   at least one detector MUST fire on this line
#   CONTROL  no detector may fire on this line
# Blank lines and lines starting with `#` are ignored.
#
# WHY THIS FILE EXISTS: a detector whose only evidence of working is a council
# transcript is a regression ANECDOTE, not a regression test. This repo already
# shipped one unprobed detector that missed 42% of the defects it was written
# to catch. Every real historical defect below is committed here so a future
# narrowing of the patterns fails CI instead of passing quietly.
#
# VOCABULARY: four tokens, most-severe first — REJECT, APPROVE-WITH-NOTES,
# APPROVE, NO-FINDINGS (.claude/rules/output-standards.md, Review Output Format
# item 4). The two NON-BLOCKING tokens are APPROVE-WITH-NOTES and NO-FINDINGS;
# a gating instruction must offer BOTH on its own line.
#
# NOT REPRESENTABLE HERE: grumpy-testing-tyrant's frontmatter `description`
# ("...rejects inadequate test suites") is a DEFECT-shaped line that check 7
# excuses via FRONTMATTER_VERDICT_EXEMPT — a file+key+word allowlist, not a
# line-level property. It is therefore deliberately absent from this corpus;
# the exemption is asserted by the reviewer files themselves passing check 7.

DEFECT	4. Never APPROVE until all issues addressed; REJECT otherwise.
#
# NOT LINE-DETECTABLE, recorded here as a known limitation rather than as a
# probe: "Verdict: APPROVE until every issue is resolved; REJECT while any
# remain." omits NO-FINDINGS with no negation word and no "only", so no
# line-level pattern can distinguish it from conformant prose. It is caught
# instead by check 7 assertion (a), which requires all four tokens somewhere
# in the reviewer's own instruction region. Line-level detection and the
# region-level assertion cover different halves of this defect class; neither
# alone is sufficient, which is why check 7 keeps both.
#
# The same limitation applies to a plain comma-separated list that simply omits
# a token — "4. Verdict: APPROVE, REJECT, or NO-FINDINGS" has no gating shape
# and no casing error, so it is line-level CLEAN and is caught only by
# assertion (a). That is why the three-token list no longer appears among the
# CONTROLs below as a shipped fleet shape: it is not a line-level defect, but
# it is no longer conformant policy either, and leaving it labelled CONTROL
# would read as an endorsement.

# Fan-Out Contract prose ABOUT the tokens — must never read as an instruction
CONTROL	**End every fan-out run with an explicit verdict line** — `REJECT`, `APPROVE-WITH-NOTES`, `APPROVE`, or `NO-FINDINGS`.
CONTROL	- `REJECT` — Critical or High findings only. Reserve it for: it is broken, it is a security or data-loss risk, or it will break something in production. If you would not hold a release for it, it is not a `REJECT`.
CONTROL	- `APPROVE-WITH-NOTES` — you found Medium/Low issues. Record them; they do not block the merge. This is the expected verdict for most reviews.
CONTROL	- `APPROVE` — reviewed, nothing worth recording.
CONTROL	- `NO-FINDINGS` — reviewed, nothing in your domain applied.
CONTROL	Report at most 5 findings, ranked by severity. Anything beyond that goes to Deferred. A long list is not a thorough review; it is an unranked one.
CONTROL	A completed run without an explicit verdict is classified Non-reporting and re-dispatched; silence is never a pass.
CONTROL	`NO-FINDINGS` is never a fallback for being unsure, under-informed, or unable to review, and it is not a synonym for `APPROVE` or `APPROVE-WITH-NOTES`: collapsing them destroys the distinction between "reviewed and found nothing" and "never reviewed".
CONTROL	Do not send availability pings or status chatter — they are not verdicts and pollute reconciliation.
CONTROL	Never use `REJECT` to signal that you could not review — `REJECT` is a finding, and spending it on a coverage gap launders "never reviewed" into "reviewed and found a problem".
CONTROL	`APPROVE-WITH-NOTES` is a distinct token, not an instance of `APPROVE`; naming one does not name the other.

# prose that would break if `block` or `condemn` were added to the BLANKET

CONTROL	A member blocked waiting on input is indistinguishable from a hung member and cannot be recovered by the orchestrator.
CONTROL	`APPROVE` — you reviewed and judge the work fit to proceed, with nothing worth recording.
CONTROL	`APPROVE-WITH-NOTES` — you reviewed and found Medium or Low issues; record them, they are non-blocking.
CONTROL	B6 condemns a member that reviewed and then gave no verdict, whereas here there is no review to report.
CONTROL	If you could not perform a proper review at all, do not emit a verdict token — say plainly what blocked you.
